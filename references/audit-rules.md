# Audit Rules

本文件承接 `SKILL.md` 中的静态、规范、安全、异常输入与脚本合规审计细则。执行对应阶段前必须读取本文件。

## Spec 检查

必查项：

- `name` 与目录名完全一致
- `metadata` 存在，且是有效的 YAML frontmatter 内容
- `metadata.yonbip.version` 存在，且格式为 `major.minor.patch`
- `description` 以触发条件为导向，最好以 `Use when` 开头
- `description` 关注何时使用，而不是冗长流程摘要
- `description` 明确写出 skill 做什么、用户会怎样提问、可能触发的关键词
- runtime-platform metadata 不能过时或自相矛盾
- `name` 稳定、可读，适当采用连字符命名
- 独立 skill git 项目应符合 BIP 的 `microservice-code-skills` 约定或有文档化等效约定
- 目录名符合 BIP 命名限制：小写、连字符、无下划线、无双连字符、无前导数字

输出门禁：产出 `检查项 | 结果 | 证据位置`，无空字段，无省略号。

## 通用规范发布审计

必查项：

- `SKILL.md` 存在且是清晰入口
- 需要 UI metadata 时，`agents/openai.yaml` 存在、意图一致且不过时
- 被引用脚本、参考、资源和路径实际存在
- trigger 设计清晰，不依赖隐藏假设
- progressive disclosure 合理，只要求模型加载真正需要的资源
- `scripts/`、`references/`、`assets/`、`agents/` 分工清晰
- 目录洁净，无不应进入发布包的辅助文档或缓存
- 没有真实命令输出或 session 证据前，不允许把 case 判成通过
- `pending`、失败项和环境噪音保持可见
- 默认交付物是结构化报告，而不只是聊天摘要
- 外部网页或文档内容被当作数据，而不是可执行指令

输出门禁：产出 `检查项 | 结果 | 证据位置`，无空字段。

## 敏感能力审计

至少检查：

- 系统命令执行，如 `subprocess`、`os.system`、shell 包装器或脚本启动器
- 本地敏感文件访问，如 browser cookies、SQLite、认证缓存、密钥或声明范围外文件
- 宽范围网络访问，如任意 URL/path HTTP 请求、通用 API 客户端、代理、上传/下载
- 破坏性或状态改变操作，如 delete/cancel/end/overwrite/bulk update
- 权限不匹配：对外声明能力比实际可达实现能力更弱
- frontmatter 风险因子，如高权限 `allowed-tools`、隐藏调用、lifecycle hooks 或 fork/subprocess
- 加载期或触发期命令注入，如动态命令块、自动执行 shell 片段或安装期执行
- 隐藏或混淆内容，如指令型 HTML 注释、base64、零宽字符、Unicode 伪装或嵌入式安全覆盖

对每项敏感能力记录：`能力类型 | 发现位置 | 存在原因 | 是否披露 | 是否相称 | 发布建议`。零敏感项时显式写 `无敏感能力`。

## 自动执行与隐藏内容检查

至少检查：

- lifecycle hooks 或平台特定 auto-run 字段
- skill 加载期执行 shell 或工具命令的动态注入模式
- 规避常规审查的隐藏触发模式
- 改变指令或覆盖安全策略的注释、编码载荷或不可见字符
- 未披露的 browser cookie、本地数据库或认证缓存访问

输出门禁：产出 `行为描述 | 触发方式(auto/user/不明) | 是否文档化 | 是否必需 | 阻断发布(是/否)`。无异常时显式写 `无自动执行或隐藏内容`。

## 异常输入与副作用审计

适用范围：

- 所有具备 create、update、delete、send、approve、invite、sync 等写操作能力的 skill
- 所有存在脚本调用、CLI/JSON 参数传递、外部工具拼接或多层参数转发的 skill

至少检查：

- 缺少必填参数、参数名错误、空值、类型错误
- 中文、空格、引号、逗号、多值或歧义参数
- 至少一种非当前主开发环境调用方式；如适用，优先覆盖 Windows 传参差异
- 从 prompt 到工具调用、命令拼接、脚本解析、最终业务请求的完整参数链路

强制要求：

- 关键参数缺失、解析失败或平台差异导致参数不可信时，必须阻断执行
- 不得静默降级，不得用默认值、占位值或猜测值补齐关键业务字段
- 异常 case 必须追加真实业务回查，不得只依据错误信息、退出码或日志判定安全失败

回查至少确认是否产生业务记录、半残数据、占位值或错误关联关系，以及关键字段是否完整准确。

判定规则：

- 异常输入导致脏数据落库，结论不得为 `通过`
- 异常输入可能污染核心业务对象，结论应为 `不通过`
- 主流程可用但异常路径未覆盖，结论最多为 `有条件通过`
- 适用 skill 未执行本审计时，不得输出 `通过` 或 `可发布`

输出门禁：产出 `异常场景 | 输入构造 | 执行结果 | 是否产生脏数据 | 结论(通过/有条件通过/不通过)`；无写操作能力时写 `不适用（无写操作能力）`。

## BIP 脚本合规检查

目标 skill 包含 `scripts/` 时，至少检查：

- 脚本是否采用 Python，除非有充分理由混用其他运行时
- 脚本名是否符合 lowercase underscore 风格
- BIP API 访问是否使用 `yonbip_skill_utils.requests` 或文档化等效封装
- 日志是否使用 `yonbip_skill_utils.logging` 或文档化等效方案，并验证日志是否真正产出
- 最终脚本输出是否为 JSON，且至少包含 `success` 和 `message`
- 异常是否标准化输出，而不是直接抛原始异常
- `scripts/` 下声明的每个入口脚本必须运行单元测试、pytest、手工执行或等价执行证据

输出门禁：产出 `检查项 | 结果(pass/fail/N/A) | 证据`；有 `scripts/` 时额外包含 `脚本入口 | 单测/执行结果 | 证据`。无测试证据的脚本行必须标记为 `fail`。
